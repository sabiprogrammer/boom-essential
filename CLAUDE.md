**Supabase connection rules (Stage 6, milestone 1):** packages `@supabase/supabase-js` and `@supabase/ssr`. Files: `lib/supabase/config.ts` (reads and validates the two public variables; errors name the variable, never its value), `lib/supabase/client.ts` (`createSupabaseBrowserClient()`), `lib/supabase/server.ts` (`createSupabaseServerClient()`: async, `server-only`, a NEW client per call bound to the request's cookies, never a module-level instance; `setAll` swallows the Server Component cookie-write error). Environment variables, in the git-ignored `.env.local` and (later) the Vercel project: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; names only in `.env.example`. Never print, log, commit or hard-code their values. Never read, request, store or name a service-role or secret key, and it must never get a `NEXT_PUBLIC_` name; when a server-only privilege is truly needed, ask first. The publishable key is public by design, so Row Level Security (not the key) protects data. **The clients themselves authenticate nothing and protect nothing:** access is decided only by `requireAdmin()` / `getAdminAccess()` and the proxy (next section). There is still no table, migration, RLS policy or data query (`tests/supabase/boundaries.test.ts` fails if one appears), pages, components, content and hooks never import `@/lib/supabase` directly (they go through `lib/auth`), `/dashboard-preview` and the enquiry form are unchanged, and `lib/supabase/proxy-client.ts` is the proxy's variant of the server client. For server-side checks use `getClaims()`, never `getSession()`. Code that calls `createSupabaseServerClient()` is request-time: keep it inside `<Suspense>` and never in `use cache`. Verify connectivity only with a throwaway script outside the repo that prints status codes, never through a public endpoint.

**Administrator authentication rules (Stage 6, milestone 2):** Supabase self-service sign-up is NOT disabled, so being signed in proves nothing: administrator access is granted only to a VERIFIED user id (`sub` from `supabase.auth.getClaims()`) listed in the server-only env var **`BOOM_ADMIN_USER_IDS`** (one or more Supabase user UUIDs, comma-separated; in the git-ignored `.env.local` and later the Vercel project; name only in `.env.example`; never `NEXT_PUBLIC_`, never printed, logged, committed or read by client code). It fails closed: a missing or empty value, or ANY malformed entry, denies everyone (`lib/auth/admin-allowlist.ts`); `user_metadata`/`app_metadata` are never used as proof; any error denies (`lib/auth/admin-access.ts`, pure and unit-tested). Administrators are created by hand in Supabase, and adding one means adding the UUID to the variable. **Flow:** `/admin/login` (public; `components/admin/LoginForm.tsx`) posts to the `signInAction` Server Action (`lib/auth/sign-in-action.ts`, core in `sign-in.ts`): email and password are re-validated server-side, `signInWithPassword`, then `getClaims()` and the allowlist; a signed-in non-administrator is signed out again; every failure shows the same generic message (no account enumeration); only then does it redirect, to a destination passed through `safeAdminRedirect()` (`lib/auth/safe-redirect.ts`: only internal `/admin` paths, never the login page). `signOutAction` (`sign-out-action.ts`) calls `supabase.auth.signOut()` (global scope) and redirects to `/admin/login`. **Protected routes:** `/admin` and every descendant except `/admin/login`; pages live in `app/admin/(protected)/` (the layout cannot guard the login page, so the login page is outside it). **Proxy:** root `proxy.ts` (Next.js 16; never `middleware.ts`) has the matcher `["/admin", "/admin/:path*"]` only, so public pages make no Supabase call; for protected paths it refreshes the session with `getClaims()` (refreshed cookies go on the request, the response AND any redirect), redirects non-administrators to `/admin/login` (with a safe `?next=`), and sets `Cache-Control: private, no-store` and `X-Robots-Tag: noindex, nofollow`; `/admin/login` passes through untouched. **The proxy is NOT the only boundary:** the protected layout, EVERY admin page, Server Action and Route Handler must call `requireAdmin()` (`lib/auth/require-admin.ts`, server-only; redirects to the login page) or, where a redirect is wrong (Route Handlers answering JSON), `getAdminAccess()` and return 401/403 themselves. Layouts are not re-run on client-side navigation, so a layout check is never enough on its own; with Cache Components the check sits inside `<Suspense>`, never at the top level of a layout. Do not add sign-up, registration, magic-link, social sign-in, password-reset or invitation features without approval (`tests/auth/admin-area-structure.test.ts` fails if a registration call, route or wording appears). `/admin` shows only a placeholder, no figures, and never imports the dashboard preview's demo data. Admin metadata is `noindex, nofollow` (`app/admin/layout.tsx`). Never log credentials, tokens or auth errors. Brute-force protection is Supabase Auth's own rate limiting, nothing custom yet. **Still to do:** tables, migrations and RLS; live enquiry and appointment data in `/admin`; the server-side enquiry handler; CSV export; audit trail; custom rate limiting if wanted. The tests in `tests/auth/` and `tests/supabase/` must be updated deliberately when any of that is added.
