**Supabase connection rules (Stage 6, milestone 1):** packages `@supabase/supabase-js` and `@supabase/ssr`. Files: `lib/supabase/config.ts` (reads and validates the two public variables; errors name the variable, never its value), `lib/supabase/client.ts` (`createSupabaseBrowserClient()`), `lib/supabase/server.ts` (`createSupabaseServerClient()`: async, `server-only`, a NEW client per call bound to the request's cookies, never a module-level instance; `setAll` swallows the Server Component cookie-write error). Environment variables, in the git-ignored `.env.local` and (later) the Vercel project: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; names only in `.env.example`. Never print, log, commit or hard-code their values. The service-role/secret key may be read in ONE file only, `lib/supabase/secret-client.ts` (approved by the owner on 2026-11-13 for the public enquiry submission; variable `SUPABASE_SECRET_KEY`), never gets a `NEXT_PUBLIC_` name, and is never requested in chat, printed, logged or committed (the owner puts it in `.env.local` and the Vercel project themselves); any other use needs approval first (`tests/supabase/boundaries.test.ts` enforces this). The publishable key is public by design, so Row Level Security (not the key) protects data. **The clients themselves authenticate nothing and protect nothing:** access is decided only by `requireAdmin()` / `getAdminAccess()` and the proxy (next section). The database schema is defined only as SQL in `supabase/` (applied to the development project) and the only data calls in the application are the `submit_enquiry` function from `lib/enquiry/server/submit-to-database.ts` and the administrator's reads and writes in `lib/admin/enquiries/queries.ts` and `enquiry-actions.ts` (`tests/supabase/boundaries.test.ts` fails if any other query appears); pages, components, content and hooks never import `@/lib/supabase` directly (they go through `lib/auth`), `/dashboard-preview` and the enquiry form are unchanged, and `lib/supabase/proxy-client.ts` is the proxy's variant of the server client. For server-side checks use `getClaims()`, never `getSession()`. Code that calls `createSupabaseServerClient()` is request-time: keep it inside `<Suspense>` and never in `use cache`. Verify connectivity only with a throwaway script outside the repo that prints status codes, never through a public endpoint.

**Administrator authentication rules (Stage 6, milestone 2):** Supabase self-service sign-up is NOT disabled, so being signed in proves nothing: administrator access is granted only to a VERIFIED user id (`sub` from `supabase.auth.getClaims()`) listed in the server-only env var **`BOOM_ADMIN_USER_IDS`** (one or more Supabase user UUIDs, comma-separated; in the git-ignored `.env.local` and later the Vercel project; name only in `.env.example`; never `NEXT_PUBLIC_`, never printed, logged, committed or read by client code). It fails closed: a missing or empty value, or ANY malformed entry, denies everyone (`lib/auth/admin-allowlist.ts`); `user_metadata`/`app_metadata` are never used as proof; any error denies (`lib/auth/admin-access.ts`, pure and unit-tested). Administrators are created by hand in Supabase, and adding one means adding the UUID to the variable. **Flow:** `/admin/login` (public; `components/admin/LoginForm.tsx`) posts to the `signInAction` Server Action (`lib/auth/sign-in-action.ts`, core in `sign-in.ts`): email and password are re-validated server-side, `signInWithPassword`, then `getClaims()` and the allowlist; a signed-in non-administrator is signed out again; every failure shows the same generic message (no account enumeration); only then does it redirect, to a destination passed through `safeAdminRedirect()` (`lib/auth/safe-redirect.ts`: only internal `/admin` paths, never the login page). `signOutAction` (`sign-out-action.ts`) calls `supabase.auth.signOut()` (global scope) and redirects to `/admin/login`. **Protected routes:** `/admin` and every descendant except `/admin/login`; pages live in `app/admin/(protected)/` (the layout cannot guard the login page, so the login page is outside it). **Proxy:** root `proxy.ts` (Next.js 16; never `middleware.ts`) has the matcher `["/admin", "/admin/:path*"]` only, so public pages make no Supabase call; for protected paths it refreshes the session with `getClaims()` (refreshed cookies go on the request, the response AND any redirect), redirects non-administrators to `/admin/login` (with a safe `?next=`), and sets `Cache-Control: private, no-store` and `X-Robots-Tag: noindex, nofollow`; `/admin/login` passes through untouched. **The proxy is NOT the only boundary:** the protected layout, EVERY admin page, Server Action and Route Handler must call `requireAdmin()` (`lib/auth/require-admin.ts`, server-only; redirects to the login page) or, where a redirect is wrong (Route Handlers answering JSON), `getAdminAccess()` and return 401/403 themselves. Layouts are not re-run on client-side navigation, so a layout check is never enough on its own; with Cache Components the check sits inside `<Suspense>`, never at the top level of a layout. Do not add sign-up, registration, magic-link, social sign-in, password-reset or invitation features without approval (`tests/auth/admin-area-structure.test.ts` fails if a registration call, route or wording appears). `/admin` shows the live Enquiries workspace and never imports the dashboard preview's demo data or state (it reuses only a tested allowlist of the preview's purely visual components and pure helpers). Admin metadata is `noindex, nofollow` (`app/admin/layout.tsx`). Never log credentials, tokens or auth errors. Brute-force protection is Supabase Auth's own rate limiting, nothing custom yet. **Still to do:** apply the migrations and the first-admin bootstrap (see "Database rules"); appointment confirmation and management in `/admin`; CSV export; custom rate limiting for the login if wanted (the enquiry handler exists since Stage 6.4). The tests in `tests/auth/` and `tests/supabase/` must be updated deliberately when any of that is added.

**Database rules (Stage 6, milestone 3; applied to the development project "Boom" on 2026-11-13 through the Supabase CLI, which is linked via the git-ignored `supabase/.temp/`; the CLI labels that project's environment "production", it is the only project and is treated as development; the one administrator is provisioned; remote pgTAP not yet run):** migrations in `supabase/migrations/` (six, timestamped, applied in order), the one-time first-administrator script in `supabase/bootstrap/first-admin.sql` (NOT a migration; placeholder UUID only, refuses to run until edited, never commit the edited copy), pgTAP tests in `supabase/tests/database/`. **Tables (public):** `enquiries` (database-generated unique `BOOM-YYYY-NNNNN` reference; `division` is the Contact form's category: general, energy, security, foods, industrial-equipment; services go in `requested_service` for energy and security, products in `requested_item` for foods and industrial equipment, both `text[]`; `phone` as typed plus `phone_e164` set by the server; statuses new, in_progress, contacted, resolved; CHECK constraints mirror the form's limits; NO price column), `appointments` (many per enquiry; the preferred date and time are immutable, so a reschedule means cancelling the open one and creating a new row with `rescheduled_from_id`; at most one open record per enquiry; statuses requested, confirmed, completed, cancelled; completed and cancelled are final; a confirmed record needs a confirmed date and time and the database stamps `confirmed_by`/`confirmed_at`), `enquiry_notes` (append-only, author set by the database from `auth.uid()`), `enquiry_status_history`, `appointment_status_history`, `activity_logs` (metadata limited by a CHECK to the keys from_status, to_status, reference and division: no personal data). **Private:** `private.admin_users` (user_id, role owner/admin, is_active) in a schema the API does not expose, closed by REVOKE and by RLS with no policies; `private.is_active_admin()` (SECURITY DEFINER, empty search_path, executable by `authenticated` only, reads `auth.uid()`, never user metadata). The database membership is a second check beside the application's `BOOM_ADMIN_USER_IDS`: an administrator needs BOTH, so keep them in step. **Access:** every public table has RLS; `anon` has no grants and no policy; `authenticated` is granted SELECT plus column-level writes (enquiries: update `status` only; appointments: create, and update status and scheduling fields; notes: insert `enquiry_id` and `content` only) and EVERY policy requires `private.is_active_admin()`, so a signed-in non-administrator or a deactivated administrator sees nothing; `service_role` (server only, for the future public submission) may insert enquiries and appointments, read them and set `phone_e164`, nothing else. Nothing can be deleted by anyone: no DELETE grants, and triggers block DELETE on enquiries and appointments (even for the owner and `service_role`) and block UPDATE and DELETE on notes, history and the activity log; removing personal data needs a reviewed retention migration. Status history and activity entries are written by SECURITY DEFINER triggers only when a status genuinely changes (the triggers use `UPDATE OF status` plus `WHEN (old.status IS DISTINCT FROM new.status)`), recording previous status, new status, the actor from `auth.uid()` (NULL when there is none) and the time. The first migration also revokes Supabase's default grants on new public tables, sequences and functions from `anon` and `authenticated`, and each table migration revokes explicitly, so a default can never open a table. **Never** put a real UUID, key or password in any SQL file (`tests/database/migrations.test.ts` fails on a non-fake UUID or a key), never run a migration or the bootstrap against a project without the owner's explicit approval, and never use `service_role` anywhere the browser can reach. Changing a status list, division or limit means changing the SQL, the Contact form allowlist (`content/enquiry-options.ts`) and the dashboard types together; the static test compares them. Applying them: see `docs/implementation-plan.md` §6.15.

**Public enquiry submission rules (Stage 6, milestone 4):** the browser never talks to the database. `components/contact/EnquiryForm.tsx` → `hooks/useEnquiryForm.ts` → `lib/enquiry/submit.ts` → `POST /api/enquiries` (`app/api/enquiries/route.ts`, a thin wire-up) → the pipeline in `lib/enquiry/server/handle-request.ts` (dependencies injected, unit-tested): same-origin check (`spam.ts`), JSON content type, size-limited body (16 KB, `read-body.ts`), honeypot (before validation, so a bot learns nothing), full server-side validation (`parse.ts`: the authority; builds a fresh object from known fields only so a client-supplied id, reference, status, source or timestamp is ignored; `text.ts` removes control and invisible characters and normalises Unicode; every category and interest slug is checked against `content/enquiry-options.ts`; at most two web links in a message; `phone-e164.ts` derives the stored +234 form), then ONE database call (`submit-to-database.ts`, the only file that imports `lib/supabase/secret-client.ts`). Wire types are in `lib/enquiry/api-contract.ts`; responses are built by `responses.ts` (fixed messages, `private, no-store`, never a database message). **Database side:** migrations `20261113110000_create_submission_support_tables` and `20261113110100_create_submit_enquiry_function`. `public.submit_enquiry()` is SECURITY DEFINER (empty search_path), executable by `service_role` ONLY, and creates the enquiry and its appointment request in one transaction (so a failed appointment leaves no enquiry); status, source, reference, ids and timestamps always come from the database and an appointment always starts `requested`. It is idempotent per browser-generated submission id (a retry or double click returns the original reference; `lib/enquiry/submission-id.ts`, made at submit time, never during render), treats the same phone, message and division within 24 hours as the same enquiry, and enforces persistent rate limits from private tables (5 enquiries an hour and 15 a day per client, 300 an hour overall; only accepted enquiries count; client addresses are stored only as a salted SHA-256 with a pepper the database generated; IPv6 is grouped by /64). Nothing in-memory is relied on. The private support tables (`private.enquiry_submissions`, `enquiry_attempts`, `enquiry_throttle_pepper`) have no API-role privileges and no policies. Visitors see the database-assigned reference in the success panel; an appointment request says it is not a confirmed booking. The success view replaces the form (reset with "Send another enquiry"). No CAPTCHA or third-party service is used (none approved). Test records created through the endpoint were fictional ("ZZ TEST ...", `@example.invalid`). **Never** add a status, id, reference or timestamp to the request, call another database function or table from the public path, or widen `submit_enquiry`'s grants.

**Admin enquiry management rules (Stage 6, milestone 5):** `/admin` (`app/admin/(protected)/page.tsx`) is the Enquiries workspace. **State lives in the address**: `?q=` (search), `status`, `division`, `page`, `enquiry=<uuid>` (the open drawer), parsed defensively by `lib/admin/enquiries/query-params.ts` (page size 10); the page awaits `searchParams` inside `<Suspense>` after `requireAdmin()`. **Authorisation is layered**: every exported read (`lib/admin/enquiries/queries.ts`) and Server Action (`enquiry-actions.ts`) calls `requireAdmin()` first, and all queries run with the SIGNED-IN administrator's own session (publishable key plus their token, `createSupabaseServerClient()`), so Postgres RLS independently requires an active `private.admin_users` row; the secret key is never used here and nothing is cached (`tests/auth/admin-area-structure.test.ts` enforces: requireAdmin in every export, no secret client, no delete, only the allowed columns written). **Writes**: only `enquiries.status` (update, guarded by `.eq("status", expected)` so two administrators never silently overwrite each other) and `enquiry_notes` (`enquiry_id` and `content` only; the author comes from the database session). The status history and activity log are written by the database triggers, not by this code; the drawer shows the activity log (`activity-text.ts`). Notes name their author only as "You" or "An administrator" because the administrator's email is not readable by the user session. **Search** (`search-filter.ts`) reduces typed text to safe words and builds one `or=(...ilike...)` per term over name, organisation, email, phone, normalised phone, reference, location and message; hostile input cannot add a filter (unit-tested, and the generated syntax was confirmed accepted by the real REST layer). Status chip counts follow the search and division filters. **Contact actions** (`contact-links.ts`, `EnquiryContactActions.tsx`) build real `tel:` and `https://wa.me/...` links from `phone_e164` (any country) or the typed Nigerian mobile number, with a follow-up message the administrator sends themselves; no usable number gives a disabled control, never a link. Loading (`WorkspaceSkeleton`, pending dimming), empty (none at all vs no match), error (`ListLoadError`, `(protected)/error.tsx`) and success/error messages after actions are all implemented. Appointment requests are SHOWN in the enquiry drawer (`AppointmentSummary`, with a "Manage this appointment" link); they are managed on `/admin/appointments` (see "Admin appointment management rules"). Components are in `components/admin/enquiries/`; logic in `lib/admin/enquiries/`. Never add a delete, never write other columns, never use the secret key here.

**Admin appointment management rules (Stage 6, milestone 6):** `/admin/appointments` (`app/admin/(protected)/appointments/page.tsx`) follows the same pattern as the Enquiries screen: state in the address (`?q=`, `status`, `page`, `appointment=<uuid>`; `lib/admin/appointments/query-params.ts`), `requireAdmin()` first in every page, read and Server Action (`lib/admin/appointments/queries.ts`, `appointment-actions.ts`; the user's own session, so RLS applies; no secret key; nothing cached), and a drawer for the open appointment. **The database's design is followed, not bent:** statuses are requested, confirmed, completed, cancelled (there is NO "rescheduled" status: a cancelled appointment that has a replacement is DISPLAYED as "Rescheduled", `transitions.ts`); `completed` and `cancelled` are final; a requested appointment can be confirmed, rescheduled or cancelled, a confirmed one completed, rescheduled or cancelled (`availableActions`); the customer's preferred date and time are NEVER written by the application. **Confirming** needs a date and time (today or later in Africa/Lagos, at most 366 days ahead; `slot.ts`), optional venue and note; the database stamps who confirmed it and when. **Rescheduling** calls `public.reschedule_appointment()` (migration `20261113120000`), a SECURITY INVOKER function that cancels the original (kept, not edited) and creates the linked replacement (`rescheduled_from_id`) in ONE transaction, optionally confirming it; because it runs as the caller, RLS and the column grants still decide who may use it, and non-administrators get "not_found". **Cancelling** is a deliberate second step; the optional reason is appended to the scheduling note (`composeCancellationNote`). Every change is guarded by the status the administrator was looking at (`.eq("status", expected)` or the function's `p_expected_status`), so two administrators never silently overwrite each other; the status history and activity log are written by the database triggers. Times are plain Lagos wall-clock values shown as stored and always labelled "Lagos time". The list is searched by the CUSTOMER (embedded `enquiries!inner` filter) and ordered soonest-first for open statuses, newest-first otherwise. **Diagnostic:** `public.am_i_active_admin()` (migration `20261113120100`, SECURITY DEFINER, answers only about the caller, authenticated only) lets `getAdminMembership()` show a notice when someone is on the allowlist but not an active administrator in the database (otherwise every list silently looks empty); if the functions were ever missing, rescheduling would answer "not available yet" and the notice would stay hidden (nothing breaks). Verified privileges on the live project: both functions are executable by `authenticated` and by `service_role` (Supabase's default function grant; `anon` is refused), and `service_role` is never used with them by the application. `tests/admin/select-columns.test.ts` checks every column the admin screens select against the SQL (a wrong column, `changed_at` vs `created_at`, once got past everything except a real run). **Never** write other columns, insert an appointment from the application, add a delete, or use the secret key here.
